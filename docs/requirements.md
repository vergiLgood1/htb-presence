# Requirements

## 1. Purpose

`htb-presence` shows a user's current Hack The Box (HTB) activity as Discord Rich
Presence, so friends/teammates can see at a glance what machine or challenge they're
working on without the user manually updating a status.

## 2. Scope

### 2.1 In scope (v1)

- Poll the HTB API on a configurable interval for the authenticated user's current
  activity (active machine/challenge session, if any).
- Translate that activity into a Discord Rich Presence payload and push it to the local
  Discord client over IPC.
- Show an "idle"/"browsing HTB" fallback state when no active session is detected.
- Load configuration (HTB token, Discord client ID, poll interval, display toggles) from
  a local config file.
- Run as a long-lived background process (CLI, no GUI in v1).
- Basic structured logging (info/warn/error) to stdout or a log file.
- Graceful reconnect if Discord closes/restarts, or if the HTB API is temporarily
  unreachable.

### 2.2 Out of scope (v1)

- GUI/system tray application (may come later — see roadmap).
- Team/guild-wide presence aggregation or leaderboards.
- Posting to Discord channels/webhooks (this is *Rich Presence* only, not a bot).
- Multi-account support (one HTB account per running instance).
- Historical activity tracking/storage.

## 3. Data source (revised)

HTB does not offer a public API for regular (non-Enterprise) accounts — only Enterprise
customers get an officially documented API. What `htb-presence` will use instead is the
same thing HTB's own web app (app.hackthebox.com) and every community HTB tool use:

- **HTB App Token** — generated by the user at `app.hackthebox.com` → Profile →
  Settings → *App Tokens*. This is the same mechanism used by `Pirrandi/htb-presence`
  (the existing Python project with the same name), `GoToolSharing/htb-cli` (Go),
  `htb-sdk`/`pyhtb` (Python), and others.
- **HTB's internal v4/v5 REST API** (`https://www.hackthebox.com/api/v4/...`,
  `https://labs.hackthebox.com/api/v4/...`) — not publicly documented by HTB, but
  reverse-engineered and documented by the community. Primary references:
  `Propolisa/htb-api-docs` (111+ endpoints via a Postman collection),
  `T-Crypt/HTB-API` (curl examples), `mxrch/htb_api` (endpoints pulled from frontend
  JS). `GoToolSharing/htb-cli` is a full Go implementation using this same API and is
  the most directly useful reference for this project, since it's in the same language.

**Consequences of this approach (must be designed for, not just noted):**

- The API is unofficial and undocumented by HTB itself — it can change or break without
  notice. See NFR-8 below.
- Using it is bound by HTB's Terms of Service, not by an official API agreement.
  Contributors should review HTB's current ToS regarding automated access before
  implementing new endpoints, and this project should stay read-mostly (polling status)
  rather than performing actions on the user's behalf where avoidable.
- There is no guaranteed rate-limit contract; the app must be conservative about polling
  frequency (see NFR-5) since limits are inferred, not published.

## 4. Functional requirements

| ID | Requirement |
|---|---|
| FR-1 | The app MUST authenticate to HTB's internal API using a user-supplied App Token (not a public API key, since none exists for regular accounts). |
| FR-2 | The app MUST poll HTB for the user's active machine/challenge session at a configurable interval. |
| FR-3 | The app MUST connect to the local Discord client via IPC and set a Rich Presence activity. |
| FR-4 | The presence MUST include, at minimum: current activity name (machine/challenge) and an elapsed-time timer. |
| FR-5 | The presence SHOULD optionally include HTB rank/points, controllable via config. |
| FR-6 | When no active session is detected, the app MUST fall back to a neutral "browsing HTB" or idle state rather than showing stale data. |
| FR-7 | The app MUST clear or update the Discord presence promptly (within one poll interval) when activity changes. |
| FR-8 | The app MUST allow the user to disable specific presence fields (privacy toggles), e.g. hide machine name, hide rank. |
| FR-9 | The app MUST retry Discord IPC connection with backoff if Discord is not running or the connection drops. |
| FR-10 | The app MUST handle HTB API errors (auth failure, rate limit, network error) without crashing, and log them clearly. |

## 5. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-1 | **Performance** — idle CPU/memory footprint should be negligible for a background process (target: <1% CPU average, <30MB RSS). |
| NFR-2 | **Reliability** — the process should be able to run unattended for days without manual restart. |
| NFR-3 | **Portability** — must build and run on Linux, macOS, and Windows. |
| NFR-4 | **Security** — HTB App Tokens must never be logged in full or committed to source control; config file should be user-readable only where the OS supports file permissions. |
| NFR-5 | **Respect inferred rate limits** — default poll interval must be conservative (≥ 30s recommended) since HTB does not publish a rate-limit contract for this API; back off aggressively on HTTP 429. |
| NFR-6 | **Simplicity of install** — single static binary + one config file, no runtime dependency installation required. |
| NFR-7 | **Testability** — HTB client and Discord client must be behind interfaces so core logic can be unit tested without live network/Discord access. |
| NFR-8 | **Resilience to API drift** — because the HTB endpoints used are unofficial and undocumented by HTB, the HTB client must isolate response parsing behind a small, well-tested mapping layer so a field rename/shape change fails loudly (clear error/log) instead of silently corrupting the presence shown to the user. |

## 6. Constraints & assumptions

- Requires the user to have the Discord desktop client running locally (Rich Presence
  over IPC is a local-client feature; it doesn't work with Discord in a browser).
- Requires an HTB account and a valid **App Token** (see §3) — there is no public API
  key to request, since HTB does not issue one for regular accounts.
- Assumes HTB's internal API exposes enough information to determine "currently active"
  machine/challenge; this must be re-verified against current community documentation
  (`Propolisa/htb-api-docs`) and, ideally, against `GoToolSharing/htb-cli`'s source
  before implementation, since the API surface may change without notice.
- Assumes a Discord application (client ID) has been registered for Rich Presence use.
- Assumes HTB's Terms of Service permit this kind of read-only, personal-use automated
  polling at the time of implementation; this should be re-checked, not assumed
  permanently true.

## 7. Success criteria (v1)

- A user can install the binary, drop in a config file with their HTB token and Discord
  client ID, run the app, and see their current HTB activity reflected on their Discord
  profile within one poll interval.
- The app survives Discord restarts and transient network issues without needing to be
  manually restarted.
